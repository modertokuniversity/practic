> **Версія 2** — синхронізовано зі схемою, яку де-факто використовує фронтенд лаб. роботи №6-7 (mock-дані в `../lab6_frontend/src/lib/mock/*`). Додано: роль `accountant`, `users.hourly_rate`, таблиці `projects` / `project_members` / `project_tasks`, поля `time_entries.project_id / task_id / created_by / pause_minutes / lunch_minutes`, нові значення enum'ів (`payroll_cost_summary`, `project_assigned`, `task_priority_changed`) і три нові views (`v_project_summary`, `v_project_workload`, `v_payroll_summary`). Усі зміни позначені коментарем `NEW (лаб. №6-7)` прямо в `01_schema.sql`/`02_seed_data.sql`.

## Як запустити базу

Потрібен встановлений Docker Desktop (у тебе вже є).

```bash
cd "lab5"
docker compose up -d
```

Це підніме два контейнери:

- **timetrack_db** — сам PostgreSQL 16, порт `5433` на хості (щоб не конфліктувати, якщо в тебе вже є локальний Postgres на 5432). При **першому** старті автоматично виконає `01_schema.sql`, потім `02_seed_data.sql` — і база вже буде повністю готова з тестовими даними.
- **timetrack_pgadmin** — веб-інтерфейс pgAdmin на `http://localhost:5050` (логін `admin@timetrack.com`, пароль `admin`), якщо хочеш подивитись на таблиці візуально, а не з консолі.

Підключення до самої бази (наприклад, з pgAdmin або будь-якого клієнта):

```
Host:     localhost
Port:     5433
Database: timetrack
User:     timetrack_user
Password: timetrack_pass
```

Щоб зайти прямо в psql з консолі:

```bash
docker exec -it timetrack_db psql -U timetrack_user -d timetrack
```

Щоб зупинити контейнери (дані залишаться в Docker-томі):

```bash
docker compose down
```

Щоб зупинити і **повністю стерти** дані (наступний `up` знову виконає init-скрипти з нуля):

```bash
docker compose down -v
```

Щоб прогнати демонстраційні запити (вони НЕ виконуються автоматично, саме тому лежать в окремій папці `queries/`, а не в `sql/`):

```bash
docker cp queries/demo_queries.sql timetrack_db:/tmp/demo_queries.sql
docker exec -it timetrack_db psql -U timetrack_user -d timetrack -f /tmp/demo_queries.sql
```

## Чому дані «детерміновані»

У `02_seed_data.sql` я навмисно уникав `random()` — усі зсуви часу прихід/відхід обчислюються формулою від `user_id` і дати. Завдяки цьому щоразу, коли хтось (ти, викладач, я) піднімає контейнер з нуля, дані виходять **однаковими** — і результати запитів у звіті завжди збігаються з тим, що реально поверне база. Якщо схочеш більш "живі" дані для курсової — заміни формули на `random()`, це один рядок.

## Загальна логіка бази (17 таблиць)

Уяви компанію: є підрозділи, в підрозділах працюють люди, люди щодня відмічають прихід/відхід, іноді йдуть у відпустку, а керівники й HR за всім цим спостерігають. Таблиці згруповані саме за цією логікою.

### 1. Організаційна структура — «хто є хто»

- **`departments`** — підрозділи компанії (Відділ розробки, Продажі, Бухгалтерія, HR). У кожного є `manager_id` — хто ним керує.
- **`positions`** — довідник посад (Розробник, QA, Бухгалтер...), спільний для всіх підрозділів.
- **`users`** — усі люди в системі: працівники, керівники, HR-адміністратор, системний адміністратор. Роль зберігається в полі `role`. Кожен користувач належить до підрозділу (`department_id`) і має посаду (`position_id`).

  Тут же виникає цікавий момент: `departments.manager_id` посилається на `users`, а `users.department_id` посилається назад на `departments`. Це нормально — просто при створенні таблиць у SQL-файлі зв'язок `manager_id` додається окремою командою `ALTER TABLE` вже після того, як обидві таблиці існують (інакше СУБД не дасть створити таблицю, що посилається сама на себе через ще не створену таблицю).

### 2. Графік і фактичний час — «хто коли має бути на роботі і хто коли реально був»

- **`shift_templates`** — шаблони змін: «Ранкова» (07:00–15:00), «Денна» (09:00–18:00), «Нічна» (22:00–06:00).
- **`department_shift_templates`** — яку зміну можна використовувати в якому підрозділі. Це та сама «таблиця багато-до-багатьох» із теорії: один підрозділ може мати кілька доступних змін, одна зміна може використовуватись у кількох підрозділах.
- **`schedules`** — плановий графік: «Іванов має працювати 2 вересня з 9:00 до 18:00». На кожного працівника максимум один запис графіка на день (це забезпечує обмеження `UNIQUE`).
- **`time_entries`** — те, що сталося **насправді**: коли людина реально натиснула «Прихід» і «Відхід». Кількість відпрацьованих хвилин (`worked_minutes`) рахується базою автоматично — тобі не треба самому це обчислювати ні на бекенді, ні на фронтенді, просто читай готове значення.

  Порівнюючи `schedules` (план) і `time_entries` (факт), можна знайти: запізнення, прогули (є графік — немає відмітки), переробки.

### 3. Проєкти й задачі — NEW (лаб. №6-7)

- **`projects`** — проєкти компанії, по яких ведеться облік часу (12 демо-проєктів: активні, на паузі, завершені, у плануванні). У кожного є `lead_id` — технічно відповідальна особа, і `budget_hours` — плановий бюджет годин.
- **`project_members`** — таблиця M:N: хто призначений працювати над проєктом. Саме тут реалізовано вимогу «керівник обирає, хто над яким проєктом працює».
- **`project_tasks`** — задачі проєкту (Kanban: `todo` / `in_progress` / `done`), з пріоритетом (`low`/`medium`/`high`/`urgent`) і виконавцем.
- **`time_entries`** отримав нові поля: `project_id`/`task_id` (до якого проєкту/задачі відноситься сесія), `created_by` (хто фактично створив запис — керівник міг відкоригувати запис підлеглого), `pause_minutes`/`lunch_minutes` (розбивка сесії таймера), і `source` тепер чітко `'timer'` (чесний трек) або `'manual'` (внесено заднім числом відповідальною особою).
- **`users.hourly_rate`** — вартість години працівника (грн/год), потрібна для розрахунку собівартості проєкту й звіту «Оплата праці» бухгалтера (нова роль `accountant`).

### 4. Відпустки й лікарняні

- **`leave_types`** — довідник: Щорічна відпустка, Лікарняний, Відгул, Відрядження.
- **`leave_requests`** — самі заявки з життєвим циклом статусів `pending → approved / rejected / cancelled`. Є поле `approver_id` — хто затвердив/відхилив.
- **`leave_balances`** — скільки днів відпустки/лікарняного залишилось у людини на поточний рік. Без цієї таблиці неможливо було б показати на фронтенді «у тебе залишилось 19 днів відпустки».

### 5. Допоміжні/системні таблиці

- **`holidays`** — календар свят. Потрібен, щоб звіти не вважали 24 серпня прогулом.
- **`notifications`** — сповіщення користувачів («вашу заявку затверджено», «співробітник запізнився»).
- **`audit_log`** — універсальний журнал: хто, що і коли змінив у системі (логін адміністратора, зміна статусу заявки тощо). Саме ця таблиця відповідає за вимогу «історія змін».
- **`reports`** — не самі звіти, а запис про те, що звіт було згенеровано (тип, період, хто, посилання на файл). Потрібно, щоб на фронтенді був «список раніше сформованих звітів», які можна перезавантажити, не генеруючи заново.

## Views — готові «заготовки» для фронтенду

Окрім таблиць, у базі є 5 звітних представлень (`views`) і одне матеріалізоване. Це, по суті, збережені SQL-запити, які можна викликати як звичайну таблицю — весь важкий JOIN/агрегація вже написані один раз у базі, а бекенду залишається просто `SELECT * FROM v_...`:

| View | Що показує | Де знадобиться на фронтенді |
|---|---|---|
| `v_time_entry_details` | кожна відмітка + розраховане запізнення | таблиця табеля, графік запізнень |
| `v_daily_department_summary` | статистика по підрозділу за день | графіки/чарти на dashboard |
| `v_leave_balance_current` | залишок відпустки по кожному | картка профілю користувача |
| `v_pending_leave_requests` | черга заявок на розгляд | dashboard керівника |
| `v_currently_checked_in` | хто зараз на роботі | live-віджет "зараз в офісі: 7 людей" |
| `v_project_summary` (NEW) | прогрес задач, факт/план годин, розмір команди по проєкту | картки метрик на `/projects/:id` |
| `v_project_workload` (NEW) | відпрацьовані години кожного учасника в розрізі проєкту | графік "Навантаження учасників" |
| `v_payroll_summary` (NEW) | години й вартість по кожному запису часу (з `hourly_rate`) | звіт «Оплата праці» на `/payroll` (фільтр по періоду додається в `WHERE` запиту) |
| `mv_monthly_department_stats` | місячна агрегація (важка) | графіки за місяць/рік; треба вручну освіжати командою `REFRESH MATERIALIZED VIEW mv_monthly_department_stats;` після завантаження нових даних |

**Важливий урок з `v_project_summary`:** перша версія цього view join'ила `project_tasks`, `project_members` і `time_entries` напряму до `projects` в одному запиті з `GROUP BY` — і це дало SUM/COUNT у сотні разів більші за реальні (fan-out: 10 задач × 5 учасників × 15 записів часу = 750 рядків комбінацій замість трьох незалежних агрегацій). Виправлено трьома окремими підзапитами, кожен з власним `GROUP BY project_id`, які потім LEFT JOIN'яться до `projects`. Класична пастка при об'єднанні кількох зв'язків 1:M одночасно — варто пам'ятати на майбутнє.

## Типовий сценарій роботи системи (як усе зв'язується докупи)

1. Адміністратор створює підрозділи, посади, облікові записи працівників (`departments`, `positions`, `users`).
2. Керівник формує графік змін на тиждень (`schedules`), спираючись на шаблони (`shift_templates`).
3. Щодня працівники тиснуть «Прихід»/«Відхід» — з'являються записи в `time_entries`.
4. Якщо працівник запізнився більш ніж на N хвилин — можна автоматично створити запис у `notifications` для його керівника (порівнюючи `time_entries.check_in` з `schedules.planned_start` — саме це вже готово порахувати в `v_time_entry_details.late_minutes`).
5. Працівник хоче у відпустку — подає `leave_requests`, керівник затверджує/відхиляє, при затвердженні можна оновити `leave_balances.used_days`.
6. HR раз на місяць формує зведений звіт — записує метадані в `reports`, а сирі дані бере з `v_daily_department_summary` / `mv_monthly_department_stats`.
7. Будь-яка значуща зміна (затвердження заявки, редагування табеля, деактивація користувача) додатково пишеться в `audit_log` — це і є «історія змін», яку адміністратор може переглянути.

## Що можна додати далі (для курсової)

Версія 1 цієї схеми свідомо не включала проєкти/задачі й розрахунок оплати праці — версія 2 (цей файл) уже додала базову версію обох речей, побачивши, що фронтенд лаб. роботи №6-7 реально їх потребує. Що можна розвинути далі:

- **Повноцінний payroll-модуль** — зараз `users.hourly_rate` і `v_payroll_summary` дають лише "оцінку вартості" на основі відпрацьованих годин; реальний розрахунок зарплати (податки, лікарняні виплати, бонуси) — окрема тема, окремі таблиці (`payroll_runs`, `salary_deductions`), краще винести в окремий модуль.
- **RBAC на рівні БД** — права ролей (`permissions.ts` у фронтенді) поки що не продубльовані як `GRANT`/`ROW LEVEL SECURITY` в Postgres; для продакшену варто додати хоча б RLS-політики на `time_entries`/`projects` за `role`/`department_id`.
- **Push/email-доставка сповіщень** — зараз `notifications` лише зберігає факт сповіщення; реальну відправку email робитиме `NotificationService` на бекенді (лаб. робота №4), читаючи цю таблицю.
- **Файлове сховище звітів** — `reports.file_url` зараз просто текстове поле-шлях; для реального застосунку варто підключити S3-сумісне сховище (MinIO в Docker — added easily поруч із Postgres).

## Коротко про сам генератор ER-діаграми

`diagrams/generate_er_diagram.js` — це не просто намальована вручну картинка, а невеликий Node.js-скрипт із функціями `table()` (малює прямокутник сутності й рахує його розміри сама) та `orthoLine()` (малює акуратні прямокутні лінії зв'язків через задані точки, без хаотичних діагоналей). Якщо в майбутньому додаси нову таблицю в схему — простіше додати новий виклик `table(...)` у цей скрипт і перегенерувати діаграму, ніж перемальовувати все вручну:

```bash
cd diagrams
node generate_er_diagram.js          # створює er_diagram.svg
magick er_diagram.svg -background white -flatten er_diagram.png   # потрібен ImageMagick
```
